## 1. プロジェクト概要

公開されている為替レート情報をAPI連携によって定期的に収集・整形しDBに蓄積し、集計結果をCSV形式やグラフで出力するETLパイプラインプロジェクト。

---

## 2. 背景・経緯 — なぜこのプロジェクトにしたか

データエンジニアとしてのキャリア形成に役立つポートフォリオとして作成する。また、IT業界において現在ニーズの高い技術として、Pythonによるデータ集計、業務自動化、API連携、DB連携、AWS、DB設計などがあり、これらの技術に習熟することも目的としている。

**プロジェクトの規模について:** ポートフォリオとしての完成、公開を優先するため、小規模なものとする。当初はPython+MySQL+Flask+AWSの大規模なWebアプリを構想していたが、挫折リスクが高いと判断し、ETLパイプラインに一点集中する方針とした。

**プロジェクトの機能について:** 必要最小限で核となるETL処理、バッチ処理、各種ドキュメントを完成させ、GitHubで公開する。

**開発ツール・手法について:** VSCode、A5M2、Notion、GitHubを使用する。VSCode上でClaude Codeで制作していく。学習のため、コードはなるべく自分で書き、AIの活用は設計方針のアドバイスやエラー解決の補助に留める。

## 3. 技術選定

### 3.1 為替レートAPI

**採用: Frankfurter API**（比較した候補: open.er-api.com ／ 日本銀行）

#### 候補比較

| 観点 | Frankfurter API ★採用 | open.er-api.com | 日本銀行（日銀） |
|---|---|---|---|
| 提供形態 | REST API（JSON） | REST API（JSON） | CSV/Excelで配布。公式の公開REST/JSON APIは無い |
| APIキー | 不要 | 不要 | 不要（ダウンロードのみ） |
| 料金 | 完全無料（商用可） | 無料（出典表示が必須） | 無料 |
| データソース | 中央銀行の公示レート（ECB等） | ExchangeRate-API社が複数ソースを集約 | 日本銀行（東京外国為替市場の相場等） |
| 過去データ | ◎ 特定日付・期間指定とも対応 | ❌ 不可 | ◎ 長期の過去分をCSVで取得可 |
| 更新頻度 | 営業日1回（平日16時CET頃／土日祝なし） | 1日1回 | 営業日次 |
| 今回の用途への適性 | ◎ 無料・キー不要・過去データ対応でETLバッチに最適 | △ 過去データを取得できない | ❌ 公式APIが無く、CSV/Excelのダウンロード・パースが必要 |

#### 候補比較

| 観点 | MySQL ★採用 | SQLite | Oracle Database | PostgreSQL | SQL Server |
|---|---|---|---|---|---|

| サーバ構成 | サーバ型 | サーバ不要 | サーバ型（重量級） | サーバ型 | サーバ型 |
| 想定用途・規模 | 小〜大規模Webの定番（OLTP） | 小規模・組込み・単一ファイル | 大規模基幹システム | 小〜大規模。分析・拡張機能に強い | 中〜大規模の企業システム |
| 普及度・情報量 | 非常に普及・日本語情報も豊富 | 普及・学習容易 | 大企業中心。学習環境は重い | 普及拡大中・DEで人気 | 国内の企業システムで普及 |

## 4. アーキテクチャ・処理フロー

### 4.1 処理フロー

全体像:
```
Extract → Transform → 品質チェック → Load(raw) → 集計 → 出力(CSV/PNG)
```

| 工程 | 入力 | 処理 | 出力 |
|---|---|---|---|
| Extract | なし | Frankfurter API へHTTPリクエストを送る | 当日レートのJSON |
| Transform | 当日レートのJSON | DataFrameに変換し、列名・型・日付を整形／クレンジング | 整形済みデータ |
| 品質チェック | 整形済みデータ | 欠損・型・異常値を検査 | 合格データ（NGは記録・除外） |
| Load（raw） | 合格データ | MySQLのrawテーブルへINSERT | 蓄積済みrawテーブル |
| 集計 | rawテーブル | 前日比・移動平均などを計算 | 集計テーブル |
| 出力 | 集計テーブル | CSV書き出し＋matplotlibでグラフ描画 | 集計CSV・グラフPNG |

### 4.3 データモデル

<!-- HINT: 全体像を1〜2文で導入（例: 「raw層に縦持ちで日次レートを蓄積し、後段で集計層を派生させる」など）。詳細は下の「設計判断」で1論点ずつ書く。 -->
raw層に日次で為替レートを蓄積する。
その後、集計層に派生させる。

#### テーブル定義

DDL は [../sql/schema.sql](../sql/schema.sql) を参照。本節では**なぜそう設計したか**を残す。

<!-- HINT: DDLそのものを貼り直す必要はない（schema.sqlにカラムCOMMENTを付けてあるため）。判断の根拠を書くことに集中する。 -->

| テーブル | 役割 | 主なカラム |
|---|---|---|
| `raw_rates` | 日次で取得した為替レートをそのまま蓄積する raw 層 | `id` / `date` / `base` / `quote` / `rate` / `created_at` |

#### 設計判断

**(1) テーブル名 `raw_rates` — 「raw 層」という考え方**

<!-- Q: なぜ「raw」とプレフィックスを付けたか？ 後段の集計テーブルとどう区別する設計か？ -->
<!-- HINT: 「ETLのうちどこまで加工済みか」を名前で示す思想。今回はraw（生）と集計を分け、生データを失わない方針を1〜2文で。 -->
rawという接頭辞をつけた理由は、加工前の生データであることを示し、集計後のデータと区別するため。

**(2) 縦持ち設計（1行=1通貨ペア）**

**採用: 縦持ち**（比較した候補: 横持ち（1行=1日・通貨ごとに列））

| 観点 | 縦持ち ★採用 | 横持ち |
|---|---|---|
| 行の単位 | 1行 = 1通貨ペア | 1行 = 1日（通貨ごとに列） |
| 通貨ペアの追加 | 行を追加するだけ | `ALTER TABLE` で列追加が必要 |
| 集計クエリ | `WHERE quote='JPY'` で1通貨に絞れる／`GROUP BY quote` で横断集計できる | 通貨ごとの列を `UNION` で展開しないと同じことができない |
| 欠損の扱い | レートが取れなかった行が無いだけ | セルが NULL になる |
| API レスポンスとの整合 | 一致（Transform はほぼ型変換のみ） | Transform 側で pivot 処理が必要 |

**(3) 主キーに サロゲートキー `id` を採用した理由**

**採用: サロゲートキー（`id INT AUTO_INCREMENT`）**（比較した候補: 複合主キー `(date, base, quote)`）

| 観点 | サロゲートキー `id` ★採用 | 複合主キー `(date, base, quote)` |
|---|---|---|
| キーの構成 | INT 1カラム | 3カラム |
| 子テーブルからの参照 | INT 1つで結合できる | 3カラムをまとめて参照する必要あり |
| WHERE句・結合の書きやすさ | `WHERE id = ...` の1値指定で済む | 3条件を AND で並べる必要あり |
| 自然キーの変更耐性 | 自然キーが変わっても主キーは変わらない（サロゲートキーの本質的メリット） | 自然キーが変わると主キー自体が変わる |
| 一意性の担保 | UNIQUE 制約を別途付与（→ (4)） | 主キー自体で担保 |

**(4)  `(date, base, quote)` に UNIQUE 制約をつけた理由**

<!-- Q: 主キーは `id`、自然キーは UNIQUE にした理由は？ なぜ複合主キーにしなかったか？ -->
<!-- HINT: 「idempotent な再実行」（同じ日を二度取り込んでも重複しない）に直結。STEP4 Phase B で予定している「date 行削除 → insert」戦略との関係も触れると◎。 -->
INSERTを再実行可能にするため(冪等性)。重複行をDELETEしてからINSERTするときの検索で利用する。

**(5) `rate` を `DECIMAL(18,6)` にした理由**

<!-- Q: FLOAT / DOUBLE ではなく DECIMAL を選んだのはなぜ？ (18, 6) の桁数の根拠は？ -->
<!-- HINT: 浮動小数点の丸め誤差、金額・レート系の定石。Frankfurter が返す実際の桁数を見て (整数部, 小数部) の余裕を決める。 -->
金融計算ではFLOAT/ DOUBLE ではなくDECIMALを使う。浮動小数点の丸め誤差が発生しないため、正確に計算できる。
(18,6)にした理由は以下の通り。
- 金融系 RDB 設計で最も普及している桁数
- Frankfurter の実データにミニマムフィットするのは(10, 5)だが余裕を持たせた

**(6) 通貨コードを `CHAR(3)` にした理由**

<!-- Q: なぜ3桁？ VARCHAR(3) ではなく CHAR(3) にした理由は？ -->
<!-- HINT: ISO 4217（USD/JPY/EUR…の3文字コード）。固定長が規格で確定しているため、可変長 VARCHAR ではなく固定長 CHAR を選択。 -->
ISO 4217 規格では｢3文字の固定長であること｣が確定しているので、可変長のVARCHAR型ではなくCHAR型を選択

**(7) `created_at` を列追加した理由**

<!-- Q: 行の「日付」としては `date` がある。なぜ別に取込日時 `created_at` を持つ？ -->
<!-- HINT: 「いつのレートか（=date）」と「いつ取り込んだか（=created_at）」の違い。後追い取込やリカバリ時の追跡、データの履歴性。 -->
`date`は｢いつのレートか｣を表すDATE型の値、`created_at`は｢いつ取り込んだか｣を表すDATETIME型の値。
- datetime型なので履歴を確認しやすい
- 過去のデータを取り込んだことがわかる

**(8) NOT NULL制約を主キー`id` 以外の全カラムにつけた理由**
- quality.pyでNULLは除外していてNULLがテーブルに入ることはないから
- NULLを他の値と区別する必要がないから
