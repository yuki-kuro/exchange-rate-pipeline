## 1. プロジェクト概要

公開されている為替レート情報をAPI連携によって定期的に収集・整形しDBに蓄積し、集計結果をCSV形式やグラフで出力するETLパイプラインプロジェクト。

---

## 2. 背景・経緯 — なぜこのプロジェクトにしたか

データエンジニアとしてのキャリア形成に役立つポートフォリオとして作成する。また、IT業界において現在ニーズの高い技術として、Pythonによるデータ集計、業務自動化、API連携、DB連携、AWS、DB設計などがあり、これらの技術に習熟することも目的としている。

**プロジェクトの規模について:** ポートフォリオとしての完成、公開を優先するため、小規模なものとする。当初はPython+MySQL+Flask+AWSの大規模なWebアプリを構想していたが、挫折リスクが高いと判断し、ETLパイプラインに一点集中する方針とした。

**プロジェクトの機能について:** 必要最小限で核となるETL処理、バッチ処理、各種ドキュメントを完成させ、GitHubで公開する。

**開発ツール・手法について:** VSCode、A5M2、Notion、GitHubを使用する。VSCode上でClaude Codeで制作していく。学習のため、コードはなるべく自分で書き、AIの活用は設計方針のアドバイスやエラー解決の補助に留める。

## 3. 技術選定

### 3.1 為替レートAPI

**採用: Frankfurter API**（比較した候補: open.er-api.com ／ 日本銀行）

#### 候補比較

| 観点 | Frankfurter API ★採用 | open.er-api.com | 日本銀行（日銀） |
|---|---|---|---|
| 提供形態 | REST API（JSON） | REST API（JSON） | CSV/Excelで配布。公式の公開REST/JSON APIは無い |
| APIキー | 不要 | 不要 | 不要（ダウンロードのみ） |
| 料金 | 完全無料（商用可） | 無料（出典表示が必須） | 無料 |
| データソース | 中央銀行の公示レート（ECB等） | ExchangeRate-API社が複数ソースを集約 | 日本銀行（東京外国為替市場の相場等） |
| 過去データ | ◎ 特定日付・期間指定とも対応 | ❌ 不可 | ◎ 長期の過去分をCSVで取得可 |
| 更新頻度 | 営業日1回（平日16時CET頃／土日祝なし） | 1日1回 | 営業日次 |
| 今回の用途への適性 | ◎ 無料・キー不要・過去データ対応でETLバッチに最適 | △ 過去データを取得できない | ❌ 公式APIが無く、CSV/Excelのダウンロード・パースが必要 |

### 3.2 データベース

**採用: MySQL**（比較した候補: SQLite ／ Oracle Database ／ PostgreSQL ／ SQL Server）

#### 候補比較

| 観点 | MySQL ★採用 | SQLite | Oracle Database | PostgreSQL | SQL Server |
|---|---|---|---|---|---|
| 種類 | オープンソースRDBMS | 組込み型（サーバレス）RDBMS | 商用エンタープライズRDBMS | オープンソースRDBMS | 商用RDBMS（Microsoft） |
| ライセンス・料金 | オープンソース・無料 | パブリックドメイン・無料 | 商用・有料 | オープンソース・無料 | 商用・有料 |
| サーバ構成 | サーバ型 | サーバ不要 | サーバ型（重量級） | サーバ型 | サーバ型 |
| 想定用途・規模 | 小〜大規模Webの定番（OLTP） | 小規模・組込み・単一ファイル | 大規模基幹システム | 小〜大規模。分析・拡張機能に強い | 中〜大規模の企業システム |
| 普及度・情報量 | 非常に普及・日本語情報も豊富 | 普及・学習容易 | 大企業中心。学習環境は重い | 普及拡大中・DEで人気 | 国内の企業システムで普及 |
| 自分の経験・資格 | 指導経験1.5年 | — | Oracle Master Silver SQL 保有 | — | 実務で使用経験あり |
| 今回の用途への適性 | ◎ 無料・普及・情報豊富で、実務に近くポートフォリオに最適 | ○ サーバ不要で手軽。本格RDBMSの実務想定としては運用面で見劣り | △ 高機能だが重量級・商用でポートフォリオにはオーバースペック | ○ MySQLと並ぶ有力候補。今回は経験のあるMySQLを優先 | ○ 実務経験は活きるが商用寄り。無料・汎用のMySQLを優先 |

## 4. アーキテクチャ・処理フロー

### 4.1 処理フロー

全体像:
```
Extract → Transform → 品質チェック → Load(raw) → 集計 → 出力(CSV/PNG)
```

| 工程 | 入力 | 処理 | 出力 |
|---|---|---|---|
| Extract | なし | Frankfurter API へHTTPリクエストを送る | 当日レートのJSON |
| Transform | 当日レートのJSON | DataFrameに変換し、列名・型・日付を整形／クレンジング | 整形済みデータ |
| 品質チェック | 整形済みデータ | 欠損・型・異常値を検査 | 合格データ（NGは記録・除外） |
| Load（raw） | 合格データ | MySQLのrawテーブルへINSERT | 蓄積済みrawテーブル |
| 集計 | rawテーブル | 前日比・移動平均などを計算 | 集計テーブル |
| 出力 | 集計テーブル | CSV書き出し＋matplotlibでグラフ描画 | 集計CSV・グラフPNG |

### 4.2 ディレクトリ構成
```
exchange-rate-pipeline/
├─ src/
│  ├─ extract.py      # API取得（Extract）
│  ├─ transform.py    # pandas整形・クレンジング（Transform）
│  ├─ quality.py      # データ品質チェック
│  ├─ load.py         # DB保存（Load）
│  ├─ aggregate.py    # 集計
│  └─ output.py       # CSV・グラフ出力
├─ main.py            # E→T→品質→L→集計→出力 を通す入口
├─ config.py          # 設定（.env の読み込み）
├─ tests/             # pytest のテストコード
├─ data/              # 出力物（CSV・PNG）
├─ docs/design.md     # 本ドキュメント
├─ archive/           # 旧Flaskコードの退避先
└─ .env / requirements.txt / README.md
```

## 6. 今後の課題・拡張候補

1. ローカルではなくAWSにデプロイする。S3など今回の目的に合うサービスを選択し、選定理由の説明もできるようになる。
2. Airflowの使い方を学び、複雑なETL処理を自動化する。
3. dbtの使い方を学び、データウェアハウス内でのデータ加工・変換処理をSQLで行えるようにする。
4. Amazon RedshiftなどのモダンなDWHの構築方法を学ぶ
